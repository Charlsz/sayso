# Sayso, all 37 cases, 27 October 2026

This report compares one answer written with Sayso to one answer written without it, for every case in `evals/evals.json`. The full wording is in `evals/runs/2026-10-27-full37.json`. The checker transcript is in `evals/reports/2026-10-27-full37-checks.txt`.

The skill, the reference files, the prompts, the fixtures, the assertions, and the checks were not changed during this experiment.

## Setup

- Date: 27 October 2026. Sessions started about 7:45 p.m. America/Chicago (UTC-5) and finished the same evening. An exact end time was not recorded.
- Model: Grok 4.7, inherited by every session. The sessions did not report a finer version string.
- Settings: not exposed. Temperature was not available.
- Runs per condition: 1.
- Cases attempted: 37. Cases completed in both conditions: 37. Skipped: none. Retries: none. Session errors: none.
- Execution: one fresh Cursor subagent per case per condition. Subagents did not share conversation history. The subagent model was `inherit`, so each one used the parent session's model.

With Sayso, the session was told to read `SKILL.md` and follow it, and to read only a reference that file pointed to. It was told not to read `evals/`, not to edit files, and to return only the deliverable. It was not given assertions or checks.

Without Sayso, the session received the same user prompt. It was told not to read files and not to apply a skill, and to return only the deliverable. It was not told to sound like Sayso or to avoid Sayso. The do-not-read line is a setup difference. It is there because the skill files are in the workspace the session can open.

Skill loading was checked after the fact in each transcript, by listing `Read` tool calls.

- All 37 Sayso sessions read `SKILL.md`.
- No baseline session read a file.
- References actually opened are listed on the cases below and in `files_read` in the run file.
- This is not a `/sayso` invocation in an ordinary chat. It does not measure whether the skill description would have been selected on its own.

Both conditions were told to return only the deliverable, so the saved text has no chat wrapper. That instruction was the same on both sides.

## How the grades were made

Each dimension is Sayso relative to the other answer: Better, Tie, Worse, or Unclear.

1. Task completion. Did it do what the prompt asked?
2. Correctness. Are the factual, technical, scientific, and code claims sound?
3. Voice and context fit. Do tone, formality, structure, and wording suit this task and this voice?
4. Completeness. Are the needed details, caveats, limits, and exceptions still there?
5. Restraint. Did it avoid needless rewriting, filler, and unsupported additions without dropping something useful?
6. Concision and clarity. Is the length and the shape right for this task?

Shorter is not automatically better. Casual is not automatically more natural. Formal is not automatically worse. An unchanged draft can be the right answer. On a review, a behavior the snippet does not show is not a confirmed bug.

The overall label is Sayso win, tie, Sayso regression, or unclear. It is a reading of the pair, not a weighted score. A case can win overall and still be worse on one dimension. Those splits are stated on the case.

## Limitations and grading bias

This is one run per condition on one model. A second round can move `sister-text`, `hash-lookup`, `order-retry`, and `load-note-review`, because those are the close calls. `order-retry` was graded a tie after counting the paragraphs (116 words and 92). The ten wins should not be read as a rate that will recur.

The Sayso sessions were told to read the file. A normal chat might not load the skill at all. The result does not measure triggering.

The baseline was told not to read files. That is a real setup difference. Transcripts show it held.

The grader knew which answer was which. Close ties were kept as ties. A reader who prefers shorter prose would mark `hash-lookup` and `order-retry` as regressions and might also mark `precision-recall` as unclear despite the factual gain. A reader who prefers explicit structure would mark `export-meeting` as a baseline win. Those are the judgments most exposed to taste. The factual splits on `precision-recall`, `get-user-review`, `status-note`, and `export-flag` do not depend on taste in the same way.

No dimension weights were chosen before the run. The overall label is not an average of the six columns.

## Recommendation

Gather more evidence before making any changes.

The skill should stay as it is for another full round. The useful differences are real and narrow: the precision exception (`precision-recall`), the overlapping `getUser` calls (`get-user-review`), lowercase left alone (`leave-unchanged-message`, `preserve-voice`), and not inventing a rollout (`export-flag`). The one regression is also narrow: a causal "so" in a finished note (`status-note`). Twenty-four of 37 pairs did not show a meaningful difference. That mix is not a reason to add another rule, and it is not a reason to relax one.

Do not retune the missing-file check from this run. It failed a baseline review that did mention an error, and it passed a Sayso review that did say an unreadable path raises. Changing the phrase list after seeing these answers would make the next comparison easier to pass. If that check is revisited later, the change has to be justified on the hand-written fixtures, not on this file.

A second round, same model, same 37 prompts, new sessions, is what would show whether the precision case and the `getUser` race happen again, and whether the causal "so" in `status-note` does too.
